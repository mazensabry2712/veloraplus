# VeloraPlus — Phase 1 Tenancy Foundation

## Status

Phase 1 is being implemented in incremental slices.

## Implemented in this slice

- Central `tenants` registry with ULID identifiers.
- Tenant lifecycle and database provisioning status fields.
- Stable tenant database naming derived from tenant ULID.
- Central tenant domain registry.
- Primary subdomain support.
- Verified custom-domain boundary in the resolver.
- Central account-to-tenant memberships with one membership per account/tenant.
- Explicit central database connection on platform identity/tenant models.
- Tenant runtime migration path under `database/migrations/tenant`.
- Tenant context service.
- Tenant database connection manager.
- Idempotent tenant database creation and tenant migration provisioning service.
- Tenant provisioning verifies the baseline `tenant_runtime` table before marking a tenant Ready.
- `tenant` middleware alias for future tenant routes.
- `tenant:create` Artisan command for local/provisioning workflows.
- `tenant:provision` Artisan command for idempotent provisioning/retry of an existing tenant.
- Feature and unit tests covering registry, membership uniqueness, domain resolution, context, and connection configuration.

## Tenant lifecycle

~~~
Platform Account
      ↓
Create Tenant Registry
      ↓
Create Primary Domain
      ↓
Create Owner Membership
      ↓
Create Dedicated Tenant Database
      ↓
Run Tenant Migrations
      ↓
Mark Database Ready
      ↓
Tenant becomes routable
~~~

Database creation is intentionally outside a long-running central transaction because database DDL such as `CREATE DATABASE` can cause implicit commits.

## Security rules

- Central platform models always use the central connection.
- Tenant-owned data must only be accessed after tenant context initialization.
- Tenant domains are resolved from the actual request host, not from user-provided tenant IDs.
- Custom domains require verification before resolution.
- No cross-database foreign keys are created.
- Tenant database names are generated by the platform from ULIDs; user input is not used directly as a database identifier.

## Package integration note

`stancl/tenancy` remains the selected tenancy library in the architecture stack. Current Packagist metadata for `stancl/tenancy` 3.10.1 lists `illuminate/support` compatibility through Laravel 13 and the package is actively maintained. The repository currently keeps the application's tenancy domain abstractions explicit so package integration does not leak vendor-specific behavior into business code.

Package integration must be installed and locked through Composer before relying on vendor-specific tenant commands or middleware. The application-level tenancy contracts in this slice are intentionally testable without coupling business logic to the package.
